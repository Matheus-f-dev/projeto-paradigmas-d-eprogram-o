# Mapeamento acadêmico: `RPG.pdf` → código

**Classificação**: **O** = obrigatório (desenvolvido no PDF); **E** = exemplo relevante do PDF; **C** = complementar (sugerido no PDF como ideia, ou exigido pelo enunciado do trabalho).
**Status**: *validado* = implementado, coberto por teste automatizado e observado na execução; *implementado* = implementado e testado, sem verificação visual dedicada.

## Diferenças conscientes em relação ao PDF

| Ponto do PDF | No projeto | Motivo |
|---|---|---|
| `CombatNotifier` é classe concreta no domínio | Interface no domínio; a classe do PDF é `TextCombatNotifier` | DIP mais forte: o domínio não depende de texto |
| `notify(String key, Object... args)` | Eventos tipados (`CombatEvent`) cujo campo `key` é a chave do PDF | Os eventos alimentam texto, animações, sons e estatísticas sem duplicar regras |
| `instanceof ComHabilidadeEspecial` | *Type guard* `possuiHabilidadeEspecial()` | Interfaces não existem em tempo de execução no TypeScript |
| Mago dos paradigmas sem mana (`Mago(nome, vida, ataque)`) | `gerarPelotao` cria magos com 10 de mana | O `Mago` do jogo sempre tem mana |
| `comVida` cria novos `Personagem` | `comVida` cria novas **fichas** imutáveis | As entidades da partida são a fonte única de verdade; o pipeline não duplica a regra de cura |
| Golpe usa só `this.ataque` | Usa o ataque total (base + arma + bônus − membros) | Integração com agregação e composição |
| Exemplo da p. 43: dois golpes de 15 matam Mike | No teste, são três | O braço decepado (composição) reduz o ataque do Demogorgon em 3; comentado no teste |
